Install

Run commands from the repository root. Python 3.11/3.12 are supported.

uv sync --dev
uv run manimux-robogui --robot yam --demo --host 127.0.0.1 --port 8086

Open http://127.0.0.1:8086. This demo does not connect hardware. Use --robot piper or --robot aloha for the corresponding asset preview.

Franka FR3: ordinary policy deployment

The Franka arm is an independent embodiment. A model worker supplies actions to the normal adapter, runtime and executor; the driver uses Franky for joint control. RPent, RLinf and Ray are not required. An agent bridge is an optional caller, not a hardware dependency. The unified RPent motion and VLA integration is described below.

Select franka_joint_policy.yaml and copy franka_example.yaml to a private station file. Bind the robot IP, gripper serial device, measured travel endpoints and policy endpoint. The assembly has one arm group: seven joint radians followed by normalized gripper opening (0 closed, 1 open). Select franka_fr3.yaml for a bare seven-coordinate arm. Verify the model variant and flange-to-TCP transform; the Robotiq example's 0.174 m offset is a controller EE-frame example, not a universal finger TCP.

# Linux robot environment; choose SDK wheels matching controller firmware.
python -m pip install -e '.[franka,robotiq,xpolicylab]'
# Install a compatible Franky build exposing JointReferenceHandle and
# JointImpedanceTrackingMotion; see the linked component's tested SDK build.
python -m manimux run \
  --config manimux/configs/examples/franka_joint_policy.yaml \
  --local /path/to/private/franka-station.yaml

The example is a recipe, not a bundled policy: supply the selected model's cameras, action interval, horizon, absolute joint action contract and matching backend identity. The separate model server uses its own environment. Keep robot.options.execute: false for feedback-only validation, which uses pylibfranka and performs no actuator writes. Enable execution only for a prepared deployment with FCI active, the arm Idle and the gripper activated. Executing connect applies the configured Franky collision thresholds; it does not home, unlock or clear faults. Arm component YAML owns native dynamics. Native impedance tracking keeps one controller active. Each accepted target is submitted unchanged, including the first. Host guards for reference steps, measured-to-target distance and measured speed default to null; bounded tests can explicitly configure a positive scalar or seven per-joint values. The example uses the shared smooth executor with braking tracking, command speed 0.15 rad/s and acceleration 0.5 rad/s², including deceleration during inference gaps. Complete policy chunks remain scheduled; rate shaping changes dispatched references. Native collision protection, model joint bounds, feedback freshness and fault checks remain active. Optional host checks do not guarantee physical acceleration or jerk. Submission is not measured arrival.

For the verified Linux x86_64 / Python 3.12 station, install the firmware-specific SDK with pip install -e '.[franka,robotiq]' -r scripts/setup/franka-linux-cp312.txt. This pins the tested wheel by SHA-256; the ordinary PyPI Franky 1.1.3 package lacks the required tracking API. Other firmware/platform combinations require a verified SDK build.

The driver restores the calling thread's scheduling policy after SDK connection and control startup. Franky's native control thread inherits the SDK's real-time priority; ordinary Python work such as camera reads and recording keeps its original priority.

Home, automatic startup moves and idle recovery are unsupported. RoboGUI disables Return Home and offers Finish rollout; shared shutdown stops and closes the owned sessions before finalizing recordings. Stop ends owned arm motion and clears the gripper's go-to request while retaining activation. See the Franka lifecycle contract and Robotiq contract for feedback freshness, explicit fault handling and SDK requirements.

RoboGUI retains the selected task prompt during action playback, including when no policy display label is configured. Native cartesian_reflex and joint_reflex errors appear as Robot collision protection triggered, with the original exception chain available. Inspect contact and current controller state before another Prepare; an available Prepare button does not certify hardware readiness.

The camera endpoint uses the existing latest-bundle PUB protocol on localhost 5556. Run vendor SDKs in their compatible environments; a station with a Python 3.10 ZED SDK can publish RGB to the Python 3.12 robot environment without importing that SDK there. Independent camera processes prevent SDK calls from delaying the transport process. Publish immutable images with their original source timestamps; repeated reads retain those timestamps. The subscriber keeps only the latest bundle and waits for all selected cameras during startup. Optional camera_meta identifies timestamp provenance: publication age is not exposure-to-action latency. The 0.5 s freshness limit remains active.

RPent motion and VLA tools

Select rpent_franka.yaml for both runtime and planner. Its experiment selects a Pi05 checkpoint recipe and the shared joint-action adapter. The same Toolkit can preposition, call the VLA, and move again in one rollout. See RPent setup for the shared entry point.

Copy the motion template to the private local directory and supply measured base-frame workspace bounds. Motion completion checks measured TCP/gripper feedback; closing contact is reported separately from task success. Pose tools retain the commanded gripper target. The example defaults to execute=false. The retired native state19/delta7 VLA bridge is not used; a model must match the selected ManiMux policy adapter.

Command limits and receive-only validation

PiPER's configured station joint_limits (radians) and normalized gripper range [0, 1] are shared automatically with the runtime. If executor.command_safety also defines position bounds, its existing 0.001 coordinate-unit tolerance is applied before intersecting with the strict station bounds and the executor's optional symmetric position cap. An empty intersection is an error. Other controllers can declare bounds through the same interface; undeclared bounds continue to use the existing configured limits.

Smooth uses these per-coordinate bounds together with its own velocity and acceleration limits and any stricter command-safety rates. It brakes before a boundary, retains the velocity of the emitted command, and rejects an infeasible state instead of clipping it into range. Inference-gap holds also respect these limits. Raw policy predictions remain available unchanged in the recording. Direct and MPC commands pass the same final validation; this does not add smoothing to those executors.

With robot.options.execute: false, command shape, configured safety limits and the controller's pure command validation still apply, without command transmission. This does not test motor readiness or successful physical execution. The resolved shared bounds, scalar cap, command-safety rates and control period are saved as meta.json: command_limits.

Use the same --local PATH on entry points that support station binding. The common camera, policy and runtime entry points support it; RoboGUI network options remain separate. Advanced model-specific launchers may instead take a model recipe as --config. See entry-point scope.

Launch

Agent-assisted managed deployment

On an installed station, start a fresh agent conversation in the checkout and ask to deploy a specific supported model/checkpoint and task, open RoboGUI, and leave preparation and execution to you. The deployment skill resolves existing recipes and station bindings. Missing physical camera mappings or an ambiguous checkpoint still require your input. This is a new conversation on a configured station; SDK installation, weights and calibration are separate setup work.

The managed path supports Linux + tmux, one runtime config, XPolicyLab WebSocket serving and camera-server streams. It reuses existing service entry points and isolated Python environments. Services may be launched locally or explicitly selected as external dependencies. Config-list studies and other serving frameworks continue to use the manual launch commands below.

# Read-only checks; no devices opened and no model weights loaded.
uv run manimux doctor \
  --config manimux/configs/experiments/pi05-latest300ep-step30000/coin/serial32.yaml \
  --local manimux/configs/local/station.yaml \
  --runtime-python envs/yam/.venv/bin/python \
  --policy-python third_party/XPolicyLab/policy/Pi_05/openpi/.venv/bin/python --json

# Start camera, RoboGUI, model and interactive runtime. Wait for manual Prepare.
uv run manimux up \
  --config manimux/configs/experiments/pi05-latest300ep-step30000/coin/serial32.yaml \
  --local manimux/configs/local/station.yaml \
  --runtime-python envs/yam/.venv/bin/python \
  --policy-python third_party/XPolicyLab/policy/Pi_05/openpi/.venv/bin/python --open --json

uv run manimux status --json
uv run manimux attach --service runtime  # detach: Ctrl-B, then D
uv run manimux down --timeout 30 --json

Substitute your recipe and installed interpreters. Camera defaults to the runtime interpreter; use --camera-python when needed. Use --output-dir to select a separate trial root. up --timeout is a readiness deadline per service. JSON results stay on stdout and progress goes to stderr. --open opens the default browser; agents can instead open the returned gui_url in their browser panel.

Hosted policy APIs such as Dream-1 (worker: dream_api) have no model service: omit --policy-python and export the key named by policy.options.api_key_env in the shell that runs up; doctor checks it.

For an existing or remote model, replace --policy-python with --external-policy; the runtime recipe and station binding select its WebSocket endpoint and expected identity. For cameras already published by another owner, use --external-camera and camera-server network sensors with capture timestamps and a positive max_frame_age_sec. A local camera-server recipe is then unnecessary. Doctor checks configuration; up/status receive camera frames and a model HELLO without requesting inference. External services and any SSH tunnels retain their existing owners, and down leaves them running. For a configured Franka experiment:

python -m manimux up \
  --config /path/to/franka-experiment.yaml \
  --local /path/to/private/franka-station.yaml \
  --runtime-python /path/to/franka-env/bin/python \
  --external-policy --external-camera --open --json

The Franka preset uses the same Prepare, warmup, rollout, Finish and recording flow. Its default recipe remains receive-only; select execution in the private runtime override after qualification. Home availability comes from the robot capability contract.

Keep one Franka FCI owner at a time. Read diagnostics from the active runtime: opening a second SDK connection can disconnect the first, even in receive-only mode. ManiMux rejects a second local connection to the same configured address before opening its SDK. Finish the owning session before a standalone diagnostic; coordinate raw SDK clients and clients on other hosts separately.

RoboGUI uses the official detailed FR3 v2.1 visual meshes. The reference assembly selects the articulated Robotiq 2F-85 display with components.gripper.options.visual_model: 2f_85 in the robot assembly YAML. Use frames when the installed tool has no matching visual model. Display selection preserves the assembly's measured mounting/TCP and normalized gripper command contract; the nominal finger animation does not measure object contact.

Private state, resolved plans and logs live under .local/deployment by default. Use the same --deployment-dir for all commands when overriding it. Repeated up reuses an unchanged healthy deployment owned by this tool. Changed configurations, partial deployments and external port owners are reported explicitly; no external process is adopted or stopped. Configuration source hashes are rechecked during startup. Restart after editing running service code. Preserve the state directory until its services have stopped.

Shared parameters

Use this guide to configure Serial, asynchronous chunking, RTC, ACT temporal ensembling, AAC, PAINT, AutoHorizon and backward-only BID, including their supported combinations. Start from an experiment that already works with your robot and policy; keep its checkpoint, cameras, action representation and executor settings.

Configure an experiment

Set inference.algorithm and inference.inference_schedule explicitly. The examples below replace the experiment's entire inference section unless described as overrides. They assume a model horizon H = 50; adjust the example windows for your model's actual H. Do not shorten policy.horizon_policy_steps to change how long a chunk executes.

You can instead load an inference preset and override its settings:

inference:
  config: ../../../inference/yam_act_serial.yaml
  algorithm: act_temporal_ensemble
  chunk_policy_steps: 8

This relative path is for an experiment under manimux/configs/experiments/<task>/<model>/. config paths are relative to the experiment YAML. Nested mappings merge; omitted fields remain inherited. Each section loads one preset, without recursive config references. When switching methods, remove incompatible inherited limits, triggers and blending. Some presets contain only parameters, so select the algorithm explicitly.

The examples use policy.action_decoding: inline (the default). Verify that the deployment's adapter and action format meet the compatibility requirements below before enabling a combination. See configuration and deployment recipes for the rest of the experiment and launch procedure.

Request schedules and triggers

inference_schedule When a new request may start
serial After the selected execution prefix finishes and the preceding response or error is processed. The robot holds its last command while waiting for inference.
single_inflight After the preceding response or error is processed, including process decoding when enabled; the current chunk may still be executing.
deadline First request immediately when its trigger permits; later requests only after the preceding request's policy.timeout_s deadline, even if its reply arrived earlier. See the algorithm-specific resolutions above.
multi_inflight Before earlier replies arrive, subject to the observation-rate cap, trigger and algorithm readiness.

Serial waits for scheduled execution time, not measured arrival at the target. Reaching policy.timeout_s alone does not release a single-inflight request; the client must return a response or error. It also does not cancel a remote model call.

request_trigger Applies to Behavior
refill Asynchronous ordinary chunking, BID, AAC and AutoHorizon Submit when remaining prepared action time is strictly below refill_threshold_s. Default for these algorithms, including multi-inflight.
continuous The same asynchronous algorithms Submit without checking remaining action time. Schedule and rate limits still apply.
progress Built-in Async with single_inflight Submit once accepted source progress reaches chunk_policy_steps, including latency-trimmed rows. Retain the full prediction while inference runs; no refill threshold or source-prefix cap.
algorithm All serial configurations, RTC, PAINT and standalone ACT Use the selected algorithm's execution/query timing. Default and required for these cases.

With multi_inflight, the server runs one model call at a time and replaces its waiting observation with the newest available one. It starts another call when a fresh observation is available; this is not parallel model execution. RTC/PAINT execution windows and ACT query intervals still limit submissions.

Hosted policy APIs: Dream-1

For a demo launched with manimux run --config ..., edit Task prompt directly in RoboGUI before Prepare Run. Prepare freezes the instruction for warmup and execution. After Finish and cleanup, edit it for the next rollout without restarting the runtime. Demo sessions hide layout and scoring controls, including Edit last evaluation. Formal --config-list studies retain their configured task instructions and evaluation workflow.

ManiMux can run a hosted API policy through its existing policy worker, asynchronous scheduler and executor, without a local model server or GPU. The first supported provider is policy.worker: dream_api. Other providers need an explicit observation/action adapter; arbitrary JSON responses are not robot commands.

Install the optional client with pip install -e '.[dream]'. Set DREAM_API_KEY in the runtime environment, never in configuration files. Dream-1 beta uses one current frame per camera (overhead and both wrists). Inference sends these images, state and task text to Dream Labs; the SDK's additional episode recording is disabled. A public 30 Hz serial example is included; see the README for startup commands. Tuned station-specific trial configurations are not distributed. Custom configurations use policy.worker: dream_api, the Dream YAM adapter and explicit playback, scheduling and execution parameters.

python -m manimux inspect --config /path/to/your/dream.yaml
python -m scripts.validation.dream_api_probe --config /path/to/your/dream-smooth.yaml --calls 3 --output /tmp/dream-api-probe.json

The probe uses synthetic observations and opens no robot or cameras. For operator-controlled deployment, use the same config with the camera server and manimux run --config ...; no policy_server is needed. The key must be present in the process that runs the policy worker. Every SDK response is saved before validation under policy.options.response_log_dir (default data/diagnostics/dream-api), including rejected responses. Each JSON record links raw actions to session/request, prompt, state, camera hashes and timing; errors identify the file and offending action values. Non-finite numbers use explicit strings and credentials are redacted. Finite gripper commands are clipped to [0,1], following the official Dream robot adapter. Raw values and affected rows remain in the diagnostic record; joint predictions are unchanged and non-finite output is still rejected. Only ordinary sampling is supported: RTC, PAINT and multi-inflight are not advertised. Smooth limits and filters commands but cannot fix stale predictions, network stalls or incorrect model trajectories. API and offline checks do not establish physical task success.

Longer transitions change the path and delay following a new prediction; this is not a velocity or acceleration cap.
inference.handoff_skip_steps 0 Intentional action-row adjustment, not a latency estimate. Positive values skip more rows. Retained rows occupy the original handoff time and extend the remaining trajectory; this does not guarantee continuity. Leave at zero unless explicitly testing this behavior.

Choose a refill threshold that leaves time for preparation, transport, inference and decoding. Outside refill mode, only the default 0.4 is tolerated and ignored; other explicit values, including null, are rejected. If a preset supplies another value, use a different preset or override it to 0.4 when changing triggers.

first_step_when_ready starts row zero when the result is accepted. Use it for the serial examples below. drop_infer_latency keeps the observation-based action clock and discards source rows whose times have passed before acceptance. Use it for the asynchronous examples. Neither setting changes the recorded observation timestamp. A late reply can have too few usable rows and be rejected.

Meaning of chunk_policy_steps

Step counts are model action rows, not control-loop ticks. The row interval dt is normally policy.action_dt_s. If policy.trajectory_duration_s is set, it overrides dt with trajectory_duration_s / (H - 1).

K rows span (K - 1) * dt between their first and last targets. Ordinary serial, serial ACT and BID additionally hold the last row for one interval, giving K * dt for K usable rows. AAC/AutoHorizon do not add that interval. Thus 12 rows at 30 Hz span about 0.367 s, or 0.4 s with the last-row hold; the control-loop rate does not change these times.

Policy and decoding requirements

  • Ordinary chunking and standalone ACT use the policy's default sampling mode. RTC, PAINT, AAC and AutoHorizon require the corresponding advertised sampling mode (rtc, paint, aac, autohorizon). BID also requires aac candidate sampling. Adding ACT does not change the base algorithm's sampling requirement. Check the model sampling matrix and the running server's capabilities; a YAML setting cannot enable a missing model hook.
  • Process decoding supports ordinary async, serial, RTC and train-time RTC without ACT, using a compatible adapter and a non-streaming schedule. Serial preserves its complete selected prefix through inference and decoding. Multi-inflight requires inline decoding.
  • Multi-inflight requires a streaming-capable client/server and adapter. The supplied path uses xpolicylab_ws, ManiMux's streaming server, and manimux.policy_adapter.joint:JointAdapter. An upstream server without the multi_inflight capability cannot run these configurations.
  • BID, serial ACT, ACT added to another algorithm, and asynchronous AAC/AutoHorizon require complete absolute-joint trajectories with inline decoding. The supplied adapter is JointAdapter; do not pass delta-joint or end-effector actions directly to it. These combinations do not support dense IK or waypoint handoffs.
  • Asynchronous AAC, AAC + ACT, and BID + AAC require policy.worker: xpolicylab_ws. Every use of AAC, including BID + AAC, needs an explicit robot.config and matching dual-arm end-effector increment statistics.
  • Custom inference.strategy plugins do not support multi-inflight, continuous requests, serial ACT or ACT composition. A model recipe that needs its own history or decoding adapter cannot gain these combinations by replacing its adapter name.

Replan after source progress

inference:
  algorithm: async
  inference_schedule: single_inflight
  request_trigger: progress
  chunk_policy_steps: 16
  action_start_mode: drop_infer_latency
  blend_policy_steps: 0

With progress, the shared chunk_policy_steps field is a replanning threshold, not a source-prefix cap. Retain the full model prediction; request a new chunk when source progress reaches 16 policy steps, including rows already dropped for observation-to-commit latency. This matches the RTC/PAINT source clock and does not promise 16 newly executed rows after each handoff.

For playback from the first returned action, use action_start_mode: first_step_when_ready. With an uncropped prediction, the 16-step threshold is counted from activation: at 10 Hz the next request starts after 1.6 seconds. The previous trajectory continues during inference. This submission threshold is separate from min_plan_hold_policy_steps, which only delays replacement by an already returned prediction.

The first request is immediate. Later requests wait for both the progress threshold and an available worker. Continue the old trajectory while inference runs, then trim the new result's expired prefix and switch on its action clock. Rejected results do not reset progress. The threshold must be smaller than the model horizon. Omit max_chunk_policy_steps and refill_threshold_s; no waypoint handoff or handoff skip is supported. Cross-chunk blending remains separate.

RTC

inference:
  algorithm: rtc
  inference_schedule: single_inflight
  chunk_policy_steps: 12
  action_start_mode: drop_infer_latency
  blend_policy_steps: 0
  rtc:
    initial_delay_policy_steps: 4
    delay_buffer_size: 10
    beta: 5.0

The rtc values above are the defaults:

  • initial_delay_policy_steps initializes latency in model steps; require 2 * initial_delay_policy_steps <= H.
  • delay_buffer_size sets the number of recent samples whose maximum predicts delay.
  • beta controls conditioning strength and must be finite and positive.
  • condition_source defaults to canonical (decoded model rows). timeline samples the accepted, blended trajectory on the observation clock. executor forecasts Smooth commands from its current filter history on the same clock, including recent issued commands. It requires standalone RTC and a stateless continuous/curve gripper without feedback guards. Unavailable tail rows receive zero weight; a missing delay prefix disables conditioning for that request. Forecasts assume the current plan remains active and nominal control cadence; they do not predict measured robot motion. Row skipping is unsupported for timeline/executor conditions.
  • initial_delay_policy_steps: null initializes from pre-Start warmup samples. To use that workflow, enable run.warmup_before_start: true, choose Activate Warmup after Prepare in RoboGUI, and use inline decoding. Without calibration samples, the initial estimate is zero. See the preset guide for warmup controls.

SAPolicy can separately select policy.adapter.ik_seed_source: previous_plan to seed IK from the accepted joint trajectory at the first decoded source row's timestamp. If that timestamp has no accepted reference, it uses the runtime seed. Subsequent rows continue from the previous IK solution. This leaves measured model observations unchanged and does not impose a joint-step limit or guarantee IK branch continuity.

Uses candidates from one policy and BID's backward criterion; no forward criterion or second policy is used.

Supported combinations

Choose one base algorithm. Add ACT with temporal_ensemble.enabled, or select AAC's execution horizon through bid.execution_horizon. Merely adding an rtc, paint or aac parameter block does not activate a second algorithm.

What ensemble adds

Standalone algorithm: act_temporal_ensemble already performs temporal ensembling. The optional combination wraps another algorithm, such as RTC, with the same kind of output fusion. It uses predictions from different inference requests for the same future action time. It does not combine measured state with actions, call another model, or add another executor.

RTC only:
Scheduler → RTC request/condition → model → adapter → Timeline → executor

RTC + ACT:
Scheduler → RTC request/condition → model → adapter → ACT ensemble → Timeline → executor

BID + ACT:
model candidates → adapter decodes each → BID selects one → ACT ensemble → Timeline → executor

The factory creates EnsembleStrategy(base_strategy, config) only when the combination is enabled. The base strategy still constructs requests. The wrapper aligns and averages overlapping predictions before Timeline commit. Reset clears both the base strategy and ensemble history.

RTC + ACT keeps RTC conditioning and adds one output ensemble. It requires blend_policy_steps: 0 so handoff interpolation is not added as well. This is a supported combination, not evidence that it improves task success. The next RTC condition uses the accepted fused timeline. No arbitrary stack of fusion algorithms is configured here.

After changing YAML, finish the current rollout and restart manimux run --config-list ... before preparing the next trial. The same model server can stay running for this flag change. coefficient: 0 still averages predictions with equal weights; it does not disable ensemble. A positive coefficient follows ACT's oldest-to-newest exponential weighting and gives older overlapping predictions more weight. Changing enabled to false does not disable the standalone act_temporal_ensemble algorithm; select another base algorithm to remove it.

Apply the same temporal_ensemble block to PAINT, BID, AAC or AutoHorizon. Require inline complete absolute-joint decoding, blend_policy_steps: 0, handoff_skip_steps: 0, and the default handoff: blend. RTC/PAINT + ACT require drop_infer_latency; serial combinations use first_step_when_ready.

The base algorithm retains its query/execution timing; ACT's query_interval_policy_steps is unused in these combinations. Only overlapping action times contribute, so serial AAC/AutoHorizon may have no effective overlap.

Which prediction rows participate

Prediction length and execution length are different. A model may predict 50 steps while this request executes only 5. The base strategy declares ensemble_scope in code; this is a developer contract, not another operator YAML setting.

Minimum plan hold time for continuous inference

Primary use: continuous multi-inflight inference, where completed predictions can replace the executing plan in quick succession. Continuous single-inflight can also benefit when inference completes rapidly. This advanced, opt-in setting limits how soon a plan may be replaced; it does not limit request frequency, change robot control frequency, or select the model prediction horizon.

For ordinary Serial or RTC workflows, keep this setting at zero unless you specifically need an additional replacement delay. Existing chunk_policy_steps and rtc.min_execute_policy_steps retain their algorithm-specific execution/request roles. Adding a hold to RTC may be redundant and can make a buffered response expire or invalidate its conditioned prefix.

By default, both single-inflight and multi-inflight replace the current plan as soon as a valid reply can be committed. To let each accepted plan execute for a minimum time while inference continues, set a positive integer inference.min_plan_hold_policy_steps. For example:

inference:
  algorithm: async
  inference_schedule: multi_inflight  # also supports continuous single_inflight
  request_trigger: continuous
  observation_hz: 30.0
  min_plan_hold_policy_steps: 4
  action_start_mode: drop_infer_latency
  blend_policy_steps: 0

The minimum starts at the accepted plan's execution start, including the start of a command_cubic blend when enabled. Four policy intervals of 20 ms give an 80 ms minimum; this does not change the model horizon or control rate. The wait ends early if the plan's available trajectory ends. The first plan starts without this wait. If no valid replacement is available when the minimum ends, the current plan continues until its remaining actions run out.

During the wait, the runtime retains the newest eligible completed reply and replaces it when a newer one arrives. Waiting does not occupy the single-inflight request slot or restart the minimum. Requests still follow the configured trigger and rate limit; continuous in this example keeps requesting throughout the wait. At handoff, decoding, candidate selection and latency trimming use the handoff time. With drop_infer_latency, rows that expired during the wait are discarded; first_step_when_ready deliberately starts row zero at acceptance.

This option requires policy.action_decoding: inline and a resolved single_inflight or multi_inflight schedule. It also works with their supported algorithm combinations; keep each method's required trigger and other constraints. Request deadlines and max_plan_age_s still apply, and Pause/Home clears the waiting reply. RTC/PAINT reject replies conditioned on a replaced plan; PAINT additionally checks that the handoff stays within its anchored prefix. Extra waiting can therefore cause rejections. Allow for it when choosing delay estimates and time limits.

This setting controls replacement timing. rtc.min_execute_policy_steps controls when RTC requests its next prediction, while chunk_policy_steps retains its algorithm-specific meaning. Leave the new setting at 0 to keep the existing behavior.

Identical request retries return saved receipts; changed arguments or overlapping calls are rejected. A timeout or cancellation waits for an acknowledged hold. Planning is drained before another call is admitted. RoboGUI Start and Pause remain authoritative. Backend history is shared between calls and resets per rollout.

Primitive planning and execution use the tool call timeout. The inference setting max_plan_age_s applies to VLA predictions. The Franka primitive example uses RPent's 5 mm position and 0.04 rad orientation completion tolerances.

A rejected VLA response reports the actual admission reason, timing and saved response location. For plan_too_old, compare observation age with max_plan_age_s; increasing the inference timeout does not extend that limit.

RoboGUI shows primitive tool names on the shared action timeline without model inference latency. Agent action shows executing, measured arrival or failure; VLA completion reports its chunk budget and still requires inspection of the task result.

RPent decisions shows the latest eight native tool choices, newest first: observe, move_to, move_delta, rotate, set_gripper, execute_policy and finish. Each entry retains the submitted target, units, VLA prompt or chunk budget and its result. Selected means the planner invoked the tool; hardware execution and arrival remain separate runtime receipts. Decision history recovers from state heartbeats after a GUI reconnect and clears for a new rollout. Full decision events remain in the rollout recording.

Motion completion checks measured TCP/gripper errors; completed VLA rows count dispatched references, not physical arrival or task success. Paths use bounded joint interpolation, not a Cartesian straight line. The current bridge supports ordinary Serial and complete joint chunks with optional pre-Start warmup; blending, specialized sampling and temporal ensemble remain unsupported.

Errors and panel width

Rollout errors identify the source: Model service, Camera / sensor, Robot / CAN, or Action decoding / IK. The persistent card shows the failure stage, known device or endpoint, reason, and next step. Enable Show original error (its state persists across error updates) for the underlying exception. Unknown errors remain explicitly unclassified; a missing CAN interface alone does not establish DFU mode or a broken motor. The top status retains the failure category while the runtime is idle. For example, a model connection refusal means check model loading and its endpoint; a missing robot interface means restore that interface before another Prepare. A camera service that fails before runtime connection must also be checked in its own terminal; camera startup and read errors include the failing camera name.

Operation failures appear in a persistent card with the operation, time and selectable error text. Live status updates do not overwrite it. Dismiss error message only hides the card; it does not reset a robot fault or send commands. Connecting to a new runtime service clears the previous service's error card; any failure reported by the new service is displayed independently. The operator panel uses native floating-panel resize handles. Drag a side edge to change its width; newer Viser versions dock it on the right automatically.

Operate each trial

Run controls stay in the same place; diagnostic Run details start collapsed. Switching method or initial pose keeps your selected layout for the same task when it remains available. Each task remembers its own selection during this GUI session.

Start/Pause show the requested state until the runtime confirms it. Prepare and Home show their current phase and elapsed time. A progress heartbeat means the reporter is alive, not that the robot has reached its target. If the heartbeat is lost, the UI marks hardware state unknown and keeps another Prepare blocked until the runtime reports completion or failure.

  1. Use Prepare Run for a free trial. For a scored trial, reset the scene, select Layout, then click Prepare Experiment; its Top reference is attached automatically.
  2. Hover over the Top layout reference and click its expand icon to fill the browser window. The image keeps its aspect ratio; press Escape or click the close button to return.
  3. Prepare → adjust layout → Activate Warmup → Start rollout. Layout stays editable until first Start. The suggested repeat updates with the selected layout. Start validates the template and freezes layout, repeat and image hash; Pause/Resume keeps that selection locked. Warmup only previews predictions; it never executes them. Keep reset and stopping rules consistent.
  4. Finish, select one score option, then Save evaluation. The task supplies every single-choice label and score explicitly. Choose one outcome; nothing is preselected.
  5. For an unusable trial, mark invalid and state the reason. Skip evaluation leaves it unreviewed.
  6. Start a fresh rollout for the next trial. Preserve failed attempts and separately identify retries.

For completion time, annotate seconds from formal Start to the success criterion, only for successful attempts. Do not substitute the full recording duration. Free rollouts have no scoring step. Optional operator notes and failure details are entered after Finish.

After Finish, camera previews remain visible and are marked Frozen. During a rollout, Stale means no new preview frame has arrived recently. Saving shows a persistent receipt. Edit last evaluation reopens the saved rubric and result; saving again preserves the previous label in revision history. Skipping an edit leaves the saved result unchanged.

If a finished experiment was skipped or the GUI was restarted, Trial setup shows Unscored experiment → Score selected experiment while the runtime is idle. It lists started, finalized, unlabelled experiments for the same task and method output directory. Select the session/rollout and score it in the existing form using its saved rubric; new YAML rules do not replace historical scoring rules. Free runs and partial attempts are excluded.

What evaluation actually reads

For a validation or dispatch failure, inspect command_rejected in the aborted rollout's .partial/events.jsonl. Metrics and aggregation

The comparison table groups attempts by the configured model/method setting. Missing values stay missing; every metric has its own eligible sample count.

Metric Input / interpretation
H-Score Mean valid human partial score; displayed as %
H-SR Human complete successes / valid success-or-failure labels
Completion time Explicit Start → success annotation, successful attempts only
NLDLJ / NSPARC Offline EE reference smoothness; verified holds use the recorded constant command. Split interruptions, duration-weight segments, then weight rollouts equally.
Handoff / 10, 20, 30-step similarity Execution-qualified reference jumps, with continuous and end-hold classes separate. Future 10/20/30-step windows require full overlap; sample counts are reported per window.
PRM Separately generated judge results; never a replacement for a missing human label

Which two points form a handoff jump?

A boundary must appear in executed ticks/plan_id transitions and match its committed plan and boundary event. A received prediction alone does not count.

  • Continuous switch (typically RTC): at the incoming committed start time t, interpolate the outgoing committed reference at t and compare it with the incoming committed first point. That incoming point is after runtime trimming/blending. This is not a difference between two raw model rows or two adjacent control ticks.
  • End-hold restart (typically Serial): compare the last verified constant held command with the incoming committed first point. Report this class separately from continuous switches.
  • Apply the selected robot FK to both joint targets. The reported jump is 1000 × ||XYZ_new − XYZ_old|| in mm, separately for each arm. It describes reference continuity, not measured robot motion.

Mean / P95 / Max: within one rollout, compute the mean, linearly interpolated 95th percentile and maximum over eligible boundaries of the same arm/class. Across a setting, Mean averages rollout means, P95 averages rollout P95s, and Max is the largest boundary. Rollouts have equal weight; the displayed P95 is not the percentile of pooled boundaries.

10 / 20 / 30 steps: compare old and new committed trajectories on the same future time grid. Each window requires complete coverage and has its own sample set; no endpoint padding. Serial can have a restart jump without a future overlap score. Aggregate valid window values within each rollout, then average rollout means. Velocity cosine excludes stationary pairs.

Enable smoothness and plots

Add this task-wide profile to the report index. The FK assembly must match the recorded robot/tool; it runs offline.

smoothness:
  robot_config: ../../../manimux/configs/embodiment/robot/yam_dual.yaml
  groups: [left_arm, right_arm]
  sample_hz: 30
  max_gap_s: 0.1
  cutoff_hz: 10
  threshold: 0.05

NLDLJ ↓ uses ln(T³ × ∫||jerk||²dt / peak_speed²); jerk stencils crossing plan changes are excluded. NSPARC ↓ uses positive spectral arc length of speed and retains switches. Both use scheduled EE references, with verified constant commands replacing historical hold placeholders. Pause/reset, identity breaks and long gaps split segments. Duration-weight valid segments, then equally weight active channels and rollouts; this is not a score of measured tracking accuracy.

The report generates handoff, overlap and outcome/smoothness figures when data is available. Colored manipulation-area overlays require a manipulation_scope profile; inference coverage must use that method's recorded state points. Speed-distribution diagnostics have a separate entry point.

Each report is a new immutable version. latest.json points to its HTML and summary. The CLI leaves raw recordings and human labels unchanged; episode-metrics.json preserves exclusions and metric provenance.

Invalid and unreviewed counts stay visible; missing metrics remain missing. Keep different rubric snapshots separate. The report CLI computes reference seams and smoothness offline; it does not run a robot or PRM inference. Report schema and metric options · PRM workflow · Speed diagnostics

Choose when IK runs

Pose-producing adapters support two modes. chunk is the default and solves the decoded chunk before Timeline commit. step keeps TCP poses in Timeline and solves only the current target inside each control tick. Joint-output adapters need no IK mode.

execution:
  ik:
    mode: step
    budget_ms: 5.0
run:
  control_timing: true

Merge these fields into an experiment with a direct executor and inline action decoding. The optional budget defaults to half the control period and must be shorter than that period. Reuse the example manimux/configs/experiments/openwam-custom/put_bottles/serial_step30000_step_ik.yaml. Existing experiments remain in chunk mode.

Step mode supports serial/async for IK adapters. OpenWAM YAM and XR1 YAM also support pose-space RTC/PAINT; Pi05 Tianji, XR1 Tianji and UMI-DP Tianji support pose-space RTC. Unsupported combinations fail at configuration validation. Smooth/MPC, joint candidate scoring, temporal ensembling, executor-based RTC forecasts, cubic joint blends, waypoint handoff and decoder diffIK substeps require chunk mode.

The current pose is interpolated with linear position/gripper and quaternion SLERP, then IK is seeded from the current measured joint state. Both arms share the budget; a failed or late solution holds both arms at the previous command. Watch the step_ik timing stage and step_ik_hold events. The budget is cooperative: native calls cannot always be interrupted, so verify control timing on the target machine. Pose-space interpolation can produce a different joint path from interpolating a pre-solved joint chunk.

Optional TCP target speed limit (off by default): set execution.ik.pose_speed_limit to a mapping with max_linear_m_s and/or max_angular_rad_s. Values must be positive and finite. Omit it or use null to disable. This setting applies to step IK only.

execution:
  ik:
    mode: step
    pose_speed_limit:
      max_linear_m_s: 0.25
      max_angular_rad_s: 0.6

The limiter bounds each target increment from the TCP pose of the last sent joint command, using one nominal control period. IK still starts from measured joints. Gripper commands keep their existing limits. Timeline and RTC/PAINT timestamps remain unchanged; sustained limiting can cause tracking lag or skipped intermediate targets. This limits the requested pose increment, not measured physical velocity. It does not implement waypoint-time stretching.

Execution ownership: Timeline owns chunk handoff and time-based reference sampling. The execution pipeline applies the optional pose limiter, resolves IK when needed, and calls the joint executor. The IK solver only solves; the pipeline handles failed solves by holding the last command. The main loop orchestrates these calls, records diagnostics, validates safety and sends the command. Neither the limiter nor IK rewrites the trajectory clock.

The runtime path is observation → policy → action adapter → inference strategy / Timeline → executor → robot. Model inference and hardware control run in separate processes. Model output, scheduled reference, executor command and measured state are distinct recorded stages.
