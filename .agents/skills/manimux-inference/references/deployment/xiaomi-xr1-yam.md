# Xiaomi XR-1 + YAM runbook

> 2026-10-09: The old screwdriver, red-object, pass-ball and offline experiment entries below were retired. These commands are historical; select a current entry from the [experiment index](../../../../../manimux/configs/experiments/README.md). Diagnostic tools now require an explicit experiment argument.


This guide covers only the XPolicyLab `Xiaomi_Robotics_1` integration. XPolicyLab includes
[official Xiaomi XR-1 source](https://github.com/XiaomiRobotics/Xiaomi-Robotics-1), so users do not need
another official repository clone. Our XPolicyLab fork maintains this adapter; it was not part of upstream
XPolicyLab. Model loading, preprocessing, and denoising still run entirely inside the standard XPolicy server.
ManiMux owns XPolicy wire transport, YAM FK/IK, and execution, without a parallel native model server.

During operation, the arms receive actions generated by full forward inference and denoising through official `Xiaomi-Robotics-1-5B`,
not initial poses, prerecorded trajectories, or mocks. XPolicy performs actual model inference; ManiMux converts
native EE deltas to YAM joint positions and schedules execution.

## Current checkpoint boundaries

Local `model_states.pt` comes from the official
[`Xiaomi-Robotics-1-5B`](https://huggingface.co/XiaomiRobotics/Xiaomi-Robotics-1-5B).
The official model card describes it as a starting point for further post-training, not a YAM policy.
The separately released RoboCasa / RoboCasa365 / VLABench weights also target specific simulated embodiments
and cannot directly drive dual-arm YAM.

## Action pipeline

```text
Three RGB views + 14-D YAM state
  -> XPolicy Xiaomi_Robotics_1
  -> 30 x 60 anchor-relative EE deltas
  -> ManiMux xr1_yam adapter FK/IK
  -> 30 x 14 absolute YAM joints
```

The native model output is not joint position. Each step contains position, axis-angle, and gripper deltas relative to the request-time end-effector anchor;
YAM FK/IK exists only in the ManiMux adapter.

The official public post-training data format declares no control frequency. Current `action_dt_s=0.033333`
(30 Hz) is a YAM deployment assumption, not a training frequency established from the XR-1 checkpoint. Future YAM
fine-tuning bundles must record native sampling Hz and use the same value in this configuration.

## Model environment

The XR-1 model service uses `envs/xr1/.venv`. With the XPolicy server, this environment needs model
dependencies plus XPolicyLab's HDF5, WebSocket, and msgpack dependencies:

```bash
cd /home/ubuntu/manimux
uv pip install --python envs/xr1/.venv/bin/python -e XPolicyLab
```

Without this step, importing `XPolicyLab.utils.process_data` first fails with
`ModuleNotFoundError: h5py`; manually installing one package at a time can still miss later wire dependencies.

## Configuration

```text
base server:    manimux/configs/policy/xiaomi-xr1/yam/base.yaml
ManiMux:        manimux/configs/experiments/put_bottles/xiaomi-xr1/yam_xiaomi_xr1_async.yaml
RTC:            manimux/configs/experiments/put_bottles/xiaomi-xr1/yam_xiaomi_xr1_rtc.yaml
step-15000 RTC: manimux/configs/experiments/assemble_screwdriver/xiaomi-xr1/yam_xiaomi_xr1_rtc_step15000.yaml
```

RTC uses FK to encode the ManiMux `30 x 14` overlap condition back into native model `30 x 60` space,
then applies PiGDM conditioning during five-step flow denoising. This is a ManiMux/XPolicy extension,
not an official Xiaomi XR-1 deployment feature. It uses an explicit sampler hook, without runtime
monkeypatching or an additional action-amplitude threshold.

The full RTC pipeline is:

```text
Old 30 x 14 absolute joint tail + soft mask
  -> Re-encode as 30 x 60 EE deltas against the new observation's FK anchor
  -> Normalize with action mean/std into model space
  -> Compute a clean estimate and VJP guidance at each XR-1 Euler denoising step
  -> Denormalize -> FK/IK -> New 30 x 14 joint chunk
```

This is sampler-level RTC, not chunk splicing. However, only a CPU mock flow has demonstrated
guidance taking effect inside `_generate`; a real conditioned GPU forward pass with the 5B model
remains unverified, so I7 can only be marked offline-complete.

`yam.json` was computed in the official format from `60` complete YAM episodes and `23,994` 30-step windows:
actions use mean/std for `30 x 60` anchor-relative EE deltas; states use q01/q99 for `1 x 60`
YAM joint/FK states. Thus **base testing does not require changing these values**; substituting official washer
demo stats would apply another machine's units to YAM.

These stats give the YAM state/action mapping a numerical definition, but are not the official 5B checkpoint's
paired post-training statistics. They match only after fine-tuning on the same YAM data and exporting weights.
XR-1 data conversion and training entry points are maintained only on the ManiMux `experiment` branch. The runtime
branch consumes previously generated checkpoint-paired `norm_stats.json`; do not overwrite the repository's base
projection stats.

## Base-checkpoint capability test

Base weights use a separate server configuration without overwriting future YAM fine-tuning; execution reuses standard ManiMux:

```bash
# offline contract check
cd /home/ubuntu/manimux
envs/yam/.venv/bin/python manimux/servers/xr1.py \
  --config manimux/configs/policy/xiaomi-xr1/yam/base.yaml \
  --check

# terminal 1: model server
envs/xr1/.venv/bin/python manimux/servers/xr1.py \
  --config manimux/configs/policy/xiaomi-xr1/yam/base.yaml

# terminal 2: no-CAN GPU/WS/FK/IK probe
envs/yam/.venv/bin/python scripts/validation/xpolicylab_yam_forward_probe.py \
  --config manimux/configs/experiments/put_bottles/xiaomi-xr1/yam_xiaomi_xr1_async.yaml
```

The probe must return finite `native_shape: [30, 60]` and `canonical_shape: [30, 14]` outputs.
Only after it passes, start cameras and have the operator run:

```bash
envs/yam/.venv/bin/manimux run \
  --config manimux/configs/experiments/put_bottles/xiaomi-xr1/yam_xiaomi_xr1_async.yaml
```

30 Hz remains a YAM comparison assumption, not official checkpoint metadata. Task capability is a
policy experiment result; shape, finiteness, WS, and FK/IK are this integration's acceptance criteria.

On 2026-08-20, the base GPU/WS/FK/IK probe passed on RTX 4090. The model loaded `1135` tensors,
produced finite native `30 x 60` output, and converted it to a finite `30 x 14` absolute joint chunk. The first
cold request took `953.0 ms`, followed by warm requests at `164.5 / 151.7 / 152.5 ms`. Thirty steps at 30 Hz
cover approximately `1.0 s`; warm inference uses about `4.6-5.0` steps, leaving headroom for default ManiMux. This evidence excludes
cameras, CAN, and arms, and does not prove base-checkpoint task success on YAM.

## Hardware operation: Base + ManiMux

Use default Async only for the first run, without RTC. Clear both arms' workspace and prepare the emergency stop; do not start a second
XR-1 server or RTC runtime concurrently.

### Terminal 1: XR-1 XPolicy model service

```bash
cd /home/ubuntu/manimux
envs/xr1/.venv/bin/python manimux/servers/xr1.py \
  --config manimux/configs/policy/xiaomi-xr1/yam/base.yaml
```

After model loading completes and `127.0.0.1:8500` is listening, run the no-CAN probe in another terminal:

```bash
cd /home/ubuntu/manimux

  --config manimux/configs/experiments/put_bottles/xiaomi-xr1/yam_xiaomi_xr1_async.yaml
```

Continue only if the probe returns finite `native_shape: [30, 60]` and
`canonical_shape: [30, 14]` outputs.

### Terminal 2: Three-camera service

Do not start another instance if a camera service already uses `5555`:


XPolicy and YAM FK/IK into joint commands. To stop normally, press
`Ctrl-C` once in the runtime terminal, wait `5.0 s` for Home and Recorder finalization, then stop cameras, model service, and RoboGUI.

## Current boundaries

Validated: configuration, weight/processor/stats paths, ordinary GPU forward inference, XPolicy WS, action codec,
ordinary FK/IK action conversion, RTC condition round trip, payload, and both sampler
guidance branches. Actual conditioned GPU RTC forward inference remains unverified. Cameras/CAN/hardware have been
started, but action-semantics acceptance failed. `model_states.pt` is a post-training starting point, not a policy proven to
complete tasks on YAM.

In the first YAM closed-loop trial on 2026-08-20, the left arm moved toward the rear of the robot. Hardware acceptance therefore
**failed**. The evidence shows only that 60D output converts to finite 14D joint chunks; it does not establish correct model EE
coordinates, left/right arm mapping, IK branches, or YAM joint semantics. Do not run this configuration on hardware again until Recorder offline replay,
stepwise EE target reconstruction, left/right coordinate-frame comparison, and joint-limit auditing are complete.
